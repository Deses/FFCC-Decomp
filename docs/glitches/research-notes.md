# Research Notes

The working state of the glitch investigation: what's established, what's open,
and where to pick up. The finished write-ups are listed in
[README.md](README.md).

## Goal

Find a GBA → GameCube path with a real payoff: player hitbox corruption ("big
chungus", walking through walls), wrong warps, or sequence breaks. The known
glitches (wrong craft, multi-take, multi-sell, CLES, GES, out-of-range
letters) are already documented and give speed, not routing.

## Established

- **The name-index/receive-buffer composition is an arbitrary MEM1 write.**
  Radar ROP executes ASCII name `0F G` (`mov r0,r6; bx r4`) and calls retail
  `Link_Write` with an unrestricted 32-bit word. The harness confirms the
  exact word on JP, EN and PAL. Channel 2 then sets channel 3's signed name
  count to `C02C`; two channel 3 continuations replace receive buffer 3's
  signed length, and each orphan `0x55` middle writes three chosen bytes at
  `payload + length`. The highest-value static target is `Game + 0xCB28`:
  while paused, a contiguous stream can set the pending-script flag, keep the
  reset flag zero, and install `startmap\0`. EN/PAL ship the debug start map;
  JP does not, but can name an existing script. The exact regional schedule is
  generated by `tools/gba_gc_write_plan.py`. Remaining gates are the stable
  retail radar row, repeated or batched raw sends, and a live two-port replay.
  See [GBA-to-GameCube Arbitrary Write](gba-gc-arbitrary-write.md).
- **Caravan data is static.** Each player's `CCaravanWork` (0xC30 bytes) lives
  in `Game.m_caravanWorkArr[9]`. PAL slot 0 is at `0x802202B0`, stride `0xC30`. Source:
  [FFCC-GES-Viewer](https://github.com/zcanann/FFCC-GES-Viewer)
  `InventoryViewerViewModel.cs` (its displayed addresses are 0x20 bytes before
  the actual object). EN starts at `0x8021F270` and JP at `0x8023BBB0`.
- **Write primitives found so far** (see [command-list-oob.md](command-list-oob.md)):
  - **A: `ChgCmdLst`, list index ≥ 8.** Writes a chosen s16 to
    `CCaravanWork + 0x204…0x402`. The compatibility overflow is one
    producer, but radar/name ROP is now stronger: route-compatible name
    `えkk7D8G` controls all 256 indices and all 65,536 values and queues the
    exact demonstrated packet `1F EE 34 12`.
  - **B: `DelCmdListAndItem`.** Writes `0xFFFF` to `CCaravanWork + 0xB6 + 2·slot`,
    where slot is any s16 (±64 KB). The write only happens after a successful
    "use". So the 16-bit value already at the target, read as an item ID, must
    have a row kind that uses the item: food `0x17D`/`0x186` via `useItem`. The
    `0x103` random path and kind `0x125` also delete. The target must not
    already be `0xFFFF`.
  - **C: `DeleteItemIdx` / `FGUseItem` / `FGPutItem` with a u8 slot.** Reach
    `+0xB6…+0x2B4` of the caravan block. The GBA sends `slot % 64`, so no
    trigger is known.
- **Items double as attack rows** (see [equipment.md](equipment.md)). This
  explains spell-as-weapon. The lunge distance field is still unidentified.
- **Marr's Pass has a JP nuke weapon.** In the observed `weapon_0` heap, gil
  7601 wrong-crafts Lilty item -102 with no materials or price. Its fixed
  attack row is fire/power 65,535, and particle bank 32 resolves to the zero
  word immediately after the particle-slot array, so spawning safely fails.
  Gil 4603 similarly gives Crystal Mail. See
  [wrong-craft-items.md](wrong-craft-items.md#marrs-pass-candidates-jp-live-memory).
- **Negative letter replies are a direct OOB write.** The signed high half of
  an item attachment reaches `DeleteItemIdx`. Index -72 writes the low half of
  `m_romWork` and creates the huge-radius state without CLES's food gate. For
  slot 0, the theoretical range reaches `eventWork[105..255]`, but not event
  flags or heap-based CFlat globals. Radar ROP now bypasses the normal gift
  selector entirely: legal JP name `kB3D G` sends value `0xFFB80001`, whose
  signed high half is -72 and nonzero low half forces the deletion. The
  stronger route-compatible form `えkk3D G` preserves the existing wrong-craft
  bytes, loads a raw word from `LIST_BUF`, adds a popped delta, and sends the
  same value; the retail harness confirms all three reply packets. Because the
  ROP call bypasses the signed-byte gift cursor, its high half may be any
  signed 16-bit index. Slot 0 can therefore write `0xFFFF` across almost all
  of `Game`, including every saved `m_eventFlags` byte and `eventWork` word.
  See [letter-reply-oob.md](letter-reply-oob.md).
- **The exact command-index write has a concrete item payoff.** Its window
  covers `m_letterCount` and both complete first `CLetterWork` records. A
  forged unclaimed attachment can carry any nine-bit item ID. After switching
  back to single player, the normal GC letter menu calls `AddItem` directly,
  allowing Ultima weapons (15/31/47/64), Dreamcatcher (60), Crystal Mail (81)
  or Force Ring (158). Firaga +2 (534) is just outside the nine-bit field.
  Backup inventory accepts arbitrary 16-bit items too, but no JP retail script
  calls `sysControl(19, ...)` to restore it. The retail Smith/map byte layout,
  not the final GBA-to-GC command, remains the shared blocker.
- **Unchecked equip index 5 directly aliases inventory slot 0.** The new
  route-compatible `えkk7D8G` chain queues `1E 05 9A 00`, storing signed item
  -102 over an occupied slot without crafting it. Indices `5+n` target normal
  inventory slot `n`; values 60/81 inject Dreamcatcher/Crystal Mail. This is
  a concrete speedrun-facing sink because -102 is the known safe 65,535-power
  Meteor phase-skip weapon. It is now secondary to the direct pending-script
  target; the real Smith/map stream remains their shared producer gate.
- **Smith OOB dispatch is currently fixed data-as-code, not arbitrary code.**
  JP screens 4-8 call Japanese strings as ARM; EN/PAL call character-table
  strings. The wrong-craft name bytes are mutable in `LIST_BUF`, but no
  signed-byte smith index points into either transfer buffer (EWRAM mirrors
  included). A full-width screen write would change that: JP 4354/init, EN
  5373/exit, and PAL 3682/main alias `LIST_BUF[0]`; from a reset/init phase,
  EN 5374 and PAL 3683 instead start at `LIST_BUF+4` and `LIST_BUF+8`.
  The known signed command-slot store falls 0x1FE bytes short of `gScreen`,
  and no source for those screen values is known. A sweep of the currently
  reachable fixed-string entries found no return, ARM-to-Thumb `bx`,
  attachment-state write, or outbound Joybus write before failure. Allowing a
  send followed by a reboot does not change that result. JP screen 4 still
  explains the pixel vomit by overwriting the smith table and VRAM. A
  stateful replay confirmed that screen 4 changes smith screen 0's init pointer
  to fixed text address `0x0201CC68`, then enters the undefined-instruction
  vector before another dispatch or useful send. Reusing the self-modified
  table would require recovery without rebooting the GBA CPU.
- **JoyBus reset creates a real continuation-before-header primitive.** The
  JP client's `Link_SendCMakeName` presents its header directly and queues five
  continuations. `Link_JoyReset` overwrites only the presented word; the queue
  survives the complete reconnect handshake. The retail JP image reproduced
  this in mGBA. With the legal name `A♪` (`41 81 F4`), the first preserved
  continuation sets `GbaCMakeInfo::m_playerSlot` to signed -12. JP also keeps
  `GbaCMakeInfo` across a disconnected character-creation port. A direct JP
  test writing `F4` to port 1's record and selecting Create hard-froze with
  repeated ISI exceptions at address zero: the fake `CCaravanWork` at
  `0x80232970` overlaps and destroys live SDK data. Hardware reset timing
  remains untested, but -12 is not a usable final creation slot. Directly
  injecting `FF` (-1) also freezes. The immediate shared gate is the virtual
  `CCaravanWork::Init` dispatch at JP `0x800EDDB4`: negative aliases lack the
  vtable pointer (`0x8022CCBC`) expected at fake-object offset zero and can
  branch to address zero. Seeding slot -1's fake base `0x8023AF80` with that
  vtable bypasses the ISI: the game requests the village and loads through the
  `c000_root` model/texture, then stalls. Remaining candidates are the model
  number store `0x2C` bytes before its heap array at `0x800EDBFC`, the script
  notification receiving -1 at `0x800EDDF0`, and the bulk `CGameWork` wipe.
  See
  [character creation](character-creation-disconnect.md#joybus-reset-can-discard-the-header-and-preserve-the-continuations)
  and the [harness](gba-joybus-harness.md).
- **The same reset ordering gives an unchecked GameCube receive-buffer
  append.** `Link_SendLetterReply` presents its header and queues the middle
  and final words. One reset removes the header; after the GC consumes the
  middle word, a second reset removes the final word that would trigger CRC.
  `JoyBus::SetRecvBuffer` then retains one byte from the first orphan and adds
  three bytes per repetition with no 0x400-byte bound. Reconnect clears the
  command queues but not this buffer. The retail JP client reproduced the
  exact middle-only transcript in the harness. The 343rd isolated middle word
  writes past the payload; port 3 reaches `m_gbaBootImage` and then thread
  records. This is a real GC overwrite, but ordinary reply bytes are heavily
  constrained and hundreds of two-reset cycles are not speedrun-viable. It is
  much more relevant as a post-GBA-execution bridge if a short callable
  payload is ever reached. Bulk-transfer splicing is blocked because reconnect
  sends `LINK_CHECK_CRC` (clearing the GBA transfer state) and retransfers send
  `LINK_CANCEL`.
- **Cross-record name continuations form an indexed GameCube write.** Channel
  2 continuation 10 reaches channel 3's packet-count high byte and continuation
  11 reaches its low byte. Separate legal JP names make the bytes independently
  selectable. Channel 3 then writes a chosen legal-name triple at
  `cmakeInfo[3] + 5 + 3*(s16)count`, covering roughly 96 KiB around `GbaQue` on
  a three-byte grid. Count `DE20` and two legal name fragments redirect
  `Joybus.m_fileBaseB` from `816F55C0` to `816FA641` in the live Tipa heap,
  inside the contiguous letter-buffer arena. `LoadMap` consequently stages a
  valid radar map over those buffers; a later list/letter builder can mutate
  it before it is downloaded again. The GBA radar parser trusts offsets and
  expands rows into `u16 line[256]` without bounding the expanded width. The
  untouched JP client now has confirmed PC control: row tokens
  `8128 0001 0203` overwrite saved LR with `0x02030001` and branch to an EWRAM
  Thumb sentinel. A second-stage harness now returns through `02010251`, pops
  controlled registers and a second PC, and executes a legal player name at
  JP `DETAIL_BUF` (`02035800`). Name `1F2F G` queues a real
  `Link_SendEvent(0, 0x42, 0x42)` word. The sibling `02010201` landing plus
  name `qB G` queues `1F 01 B8 FF`, directly installing command reference -72.
  More importantly, `kB3D G` queues a complete letter reply with attachment
  value `0xFFB80001`, causing the GC to call `DeleteItemIdx(-72)` without the
  CLES food-kind check. Thus the useful GBA-to-GC payload is proved; the retail multi-port/reset
  schedule and one GC smith layout satisfying the complete map header/ROP row
  remain to be demonstrated. See
  [JP Character-Name Indexed Writes](gba-name-indexed-write.md).
- **Smith records contain exact radar-PC grammar, but OOB rows are
  state-dependent.** `MakeSmithData` copies 0x38-byte records containing price,
  material/count, result-ID and result-metadata halfwords. A live Tipa scan
  found exact two-record returns to `02010251` and `02010201`, and tens of
  thousands of plausible map-header windows. The record IDs and wrong-craft
  gil producers changed across heap snapshots, so these are solver inputs,
  not stable recipes. `tools/gba_smith_radar_scan.py` searches individual or
  mixed tribes, header windows, and full register/name chains.
- **JP names contain a confirmed send-before-crash payload, but cannot point
  to themselves.** The legal seven-character name `ア2xq4?z` loads a useful
  selector from the table preceding `gSmithScreens`, branches into the IWRAM
  interrupt dispatcher and deterministically reaches the Thumb
  `Link_JoyIntr` handler. With JoyBus send status set, an emulation using the
  live JP RAM image popped a sentinel queue word into `REG_JOY_TRANS` before
  later unstable execution. The shorter `n4?z` is a generic ARM-to-Thumb
  bridge but depends on a genuinely pending interrupt. This is still only a
  payload for a future exploit: smith screen 5378 loads the first name word as
  a function pointer, and no legal JP name can put an EWRAM/IWRAM/multiboot
  high byte in that word. A three-byte name plus the following newline makes
  only a useless `0x0Axxxxxx` GamePak-ROM pointer. No reachable fixed-string
  store writes `DETAIL_BUF` into the dispatch table, and the payload sends an
  existing queued word rather than constructing an arbitrary command.
  A full-width `gScreen = -12131` would also work without a table overwrite:
  its JP init dispatch fetches an existing `0x02035800` literal at
  `0x02002344`. The normal menu event remains limited to an `s8`.
- **Compatibility overflow now has a proven outbound sink.** A fifth family
  name begins at `gSession.favorites`; its tenth byte overwrites signed
  `cmdSlotCount`. In the JP harness, byte `E8` plus the Command List's Up wrap
  emitted `1F E7 FF FF`, so `ChgCmdLst` writes `0xFFFF` at caravan `+0x3D2`
  (name bytes 8-9) before the bad screen can crash. Normal character creation
  still produces exactly four entries, which is the retail gate. Across all
  valid JP NPC names, the possible write indices are 64-147, 168, 184, 214,
  and 231; useful-looking synthetic targets such as letter-count index 243
  are not naturally selectable. The radar-object decoder separately trusts
  its count and could overrun toward `gScreen`, but the GameCube producer scans
  exactly 32 records and cannot exceed the GBA's 32-entry capacity.
- **Window overflow is close, but currently only a screen-1 curiosity.**
  `gSavedScreen` is eight bytes after `gWindows[5]`. A 54-answer letter would
  make the answer initializer's window-1 item loop write `1` to
  `gSavedScreen`, while also replacing `gSubMode` with a text pointer. The live
  route letter has only two answers, the name alphabet has no newline, and no
  OOB letter with the required answer block is known. This cannot supply the
  full-width screen values needed for buffer dispatch.
- **Negative smith screen -16 is a clean letter-state alias.** The screen
  tables are contiguous, so `gSmithScreens[-16]` is the field table's
  `LetterScreen_Update` triple in every region. It supplies the complete
  gift-to-send transition that positive JP screen 11 lacks. The missing setup
  is an `EVT_OPEN_MENU` argument byte `0xF0` or an equivalent write to
  `gSavedScreen`; no retail sender was found.
- **The submenu table supplies a concrete OOB open-letter request.** Smith
  screen 10 eventually calls `LetterRead_Main`; if `sLetterSel` is still -1,
  its u8 request argument becomes 255. `FGLetterOpen(N)` ORs `0x80` at
  `CCaravanWork + 0x3EC + 12*N`. Index 255 only reaches the next character's
  transient equip-effect flags (or a monster timer from save slot 8), so it
  has no route payoff yet. Smith screen 9 could choose any u8 index from a
  forged letter count. The strongest targets are 192-202, which OR `0x8000`
  into inventory slots 3, 9, ... 63 of the next save-slot character and thus
  manufacture persistent negative items. If array slot 0 were active, the
  current slot-1 item 385 would become -32383, but its Marr's Pass row is
  non-damaging particle garbage; ordinary item IDs 0-1204 contain no useful
  food or safe nuke after the transform. The live port-0 pointer currently
  names array slot 1, and its following slot is empty. See
  [GBA/GC trust](gba-gc-trust.md#wrong-menu-910-a-strided-gamecube-bit-write).
  The same indices reinterpret six adjacent next-character items as an entire
  letter header/attachment/four-variable record. This can select a stock JP
  template and inject a selected caravan name or table string into
  `DETAIL_BUF`. It is a real GC-to-GBA payload compiler, but exhaustive valid
  substitutions produce at most a 42-byte line, far below the letter reader's
  256-byte stack buffer. OOB substitution indices remain crashy theory.
- **A forged letter count has a clean local producer, but screen 9 has a
  timing gate.** A real letter-list download leaves `DATA_LETTER_LIST` set.
  `CmdListScreen_BuildCandidates` then replaces the first words of `LIST_BUF`
  with candidate slot halfwords without clearing that bit, producing a huge
  positive count whose shifted name pointer folds through the EWRAM mirror.
  Normal entry to Letters calls `LetterScreen_Setup`, clears the bit, and
  requests a real list. The open experiment is saving screen 9 in the short
  interval after the main menu selects it but before that setup runs, while
  also satisfying the smith dialogue pause race.

## Open

1. Can a powered JP GBA be forced through the name-header reset window against
   the retail GameCube parent? Test `A♪`, verify that `GbaCMakeInfo` becomes
   slot -12, then determine whether `ChgModel(-12)` survives. A full GBA CPU
   reboot is not equivalent because it clears `sTxQueue`.
2. Can a retail-created character acquire a fifth nonzero relationship word?
   The GBA path from that fifth name to command index ≥ 8 is now proven. The
   radar-ROP lab independently emits item-use slot 166 and signed command
   reference -72; its remaining problem is the retail smith/map producer, not
   the final packet.
3. Which field drives the weapon lunge (movement range −1)?
4. Can menu byte `0xF0` (smith screen -16) be injected, or can `gSavedScreen`
   be made -16? This runs the complete letter state machine. The older screen
   11 route still needs both its preservation trick and a transition into
   `LetterSend_Main`. Either route also needs a negative gift selection.
5. Can any GBA-side OOB store write a full-width `gScreen` value? Values 4354
   (JP), 5373 (EN), or 3682 (PAL) make smith dispatch take a function pointer
   from the mutable `LIST_BUF`, potentially converting name/list reuse into a
   control-flow primitive.
   Direct wrong-menu dispatch still aliases the name word as a pointer rather
   than branching to the buffer. Radar ROP now supplies the missing branch to
   `02035801`; legal names `1F2F G` and `qB G` are confirmed payloads.
6. What exact frame window lets a letter pause hide menu 11 (joybus state
   machine)?
7. EN character creation: why does a GBA power-off on the last frame build
   the wiped record? Needs the EN `CalcCharaSelect`
   (see [character-creation-disconnect.md](character-creation-disconnect.md)).
8. Guest return power-off: test on hardware
   (see [guest-transfer.md](guest-transfer.md)). Also check whether guests get
   a family in Tipa.
9. Double craft: confirm whether the material loop at gil 4296 trips the GBA's
   30-frame reply timeout (see [wrong-craft-items.md](wrong-craft-items.md)).
10. Test 7601 → -102 in Marr's Pass without GES: verify reload stability,
    stale-result-slot equipping, inventory-sort survival, and the Meteor
    Parasite one-hit ending.
11. Find a clean Marr's Pass Dreamcatcher or another weapon using its -1
    movement animation. The two current Dreamcatcher rows have destructive
    material loops.
12. Particles: what a junk particle definition does beyond being drawn.
13. Frame-advance the smith screen-9 entry window. Prime `LIST_BUF` through
    Command List while retaining `DATA_LETTER_LIST`, then test whether the
    pause/mode packets can land after `gScreen = 9` but before
    `LetterScreen_Setup`. First use index 171 as a reversible memory-visible
    proof, then evaluate indices 192-202 against a deliberately prepared next
    character.

## Live memory (JP, Dolphin)

- Item table `0x80979FC0`; caravan *n* at `0x8023BBB0 + n × 0xC30`; particle
  slot table `0x802B4600`. JP globals sit about `0x1B900` above PAL's.
- In the current session `Game.m_scriptFoodBase[0]` is `0x8023C7E0`
  (caravan array index 1). Its screen-10/index-255 write target is therefore
  `0x8023D7C0`, the next caravan's `m_equipEffectFlags`; it currently reads 0.
- Common GBA globals often match across regions (`gSession` is `0x03002CA0`),
  but file-local letter/smith variables do not. For JP use
  `gba/config/GCCJGC/cli/symbols.txt`; for example `sLetterGiftTop` is
  `0x030027B0`, versus `0x030027F0` in EN/PAL.
- Dolphin keeps each GBA's EWRAM and IWRAM in one 0x48000-byte private region,
  tagged `GCCJGC` at +0xAC with the port number at +0xC5.
